# Proposition technique V0.5 — observation des challenges

13 octobre 2026. Branche `feat/v0.5-challenge-observation`, créée après le push
vérifié de la V0.4.1 `7a823ca58b5898d3231408ebece4deb01a5dbbdd`.
La référence de non-régression est **1 829 tests réussis**, avec les essais réels
et limites décrits dans [verification.md](verification.md).

Ce document conserve la proposition initiale, avant implémentation. L'état des
lots désormais développés est décrit dans [gen5-rule-observation.md](gen5-rule-observation.md)
et [verification.md](verification.md) ; les tableaux ci-dessous décrivent la base
V0.4.1 et les objectifs, pas une certification de toutes les fonctions V0.5.
La priorité est Blanc FR rev0 (`IRAF`, `white_fr_rev0`), puis une validation
séparée pour chaque autre jeu. Aucune écriture RAM n'est prévue dans ces lots.

## Capacités affichées par règle

Les cinq mentions demandées doivent rester distinctes :

| Mention | Signification proposée |
| --- | --- |
| Configurée | La règle et ses paramètres sont figés dans cette partie |
| Suivie automatiquement | Les observations nécessaires sont disponibles pour ce jeu et cette session ; préciser les situations couvertes |
| Violation détectable | Un contrôle implémenté peut relever un écart à partir de ces observations ; une donnée manquante ne vaut pas conformité |
| Application stricte techniquement possible | Une méthode d'application a été documentée et validée séparément ; cela ne signifie pas qu'elle est activée |
| Non disponible | Une source, un lecteur, une identité ou une donnée manque ; afficher la cause et le suivi manuel possible |

Ce sont des dimensions complémentaires, pas une progression automatique de
« configurée » vers « stricte ». Ajouter à chaque capacité sa portée
jeu/région/révision, sa source et son niveau de preuve : documenté, synthétique,
échantillon réel. Une déconnexion suspend le contrôle, sans déclarer une victoire,
une mort ou une capture. Le catalogue `implementation_status` décrit aujourd'hui
une intention globale ; il ne suffit pas à décrire les capacités d'une session.

## État actuel et cible

La colonne détection décrit **ce qui existe dans les parties V0.4.1**, puis le
prochain travail. Aucun des mécanismes stricts ci-dessous n'est établi ou activé.
« Strict » dans Monotype désigne uniquement la convention du type principal.

| Règle / mode | Configurée actuellement | Suivi et détection actuels dans une partie | Cible V0.5 ; application stricte |
| --- | --- | --- | --- |
| Classique | Oui, zéro règle | Équipe, zone disponible, temps et historique ; captures/badges manuels | Conserver ; contrainte sans objet |

| Randomizer | Oui, état prévu | Aucune transformation de ROM ni vérification de résultat | Étude ci-dessous ; transformation hors jeu distincte d'une contrainte RAM |

Hardcore assemble déjà Nuzlocke, mort permanente, Species Clause, Level Cap et
interdiction d'objets dans `data/presets.json`. Son état doit être présenté règle
par règle : le preset ne rend pas les objets automatiquement détectables.
Les combinaisons personnalisées conservent seed, paramètres, dépendances et
incompatibilités de `RuleEngine` et `ChallengeEngine`. Un preset ne doit pas
réactiver une règle interdite ou remplir une donnée inconnue.
Les conflits sémantiques à traiter, comme Nuzlocke combiné à une limite supérieure
à une capture par zone, doivent être expliqués avant création. Aucun arbitrage
nouveau ne doit changer silencieusement les parties existantes.

## Intégration dans l'architecture existante

Conserver Profile comme modèle, Run comme aventure, et `rules_snapshot` figé.
Les points d'intégration existants sont :

| Composant actuel | Travail proposé |
| --- | --- |
| `app/bridge/protocol.py`, `app/events/game_event.py` | Garder validation de session, séquence, jeu et valeurs inconnues ; n'étendre le protocole que pour des données sourcées |
| `app/services/run_controller.py` | Transmettre les observations utiles au worker du run actif, au-delà de l'équipe et de la zone actuellement consommées |
| `app/services/run_tracking_service.py` | Garder un seul propriétaire des mutations et de l'autosave ; produire les états et événements des règles depuis les observations validées |
| `app/core/nuzlocke_tracker.py`, `app/services/tracking_service.py` | Extraire seulement la logique de rencontre nécessaire, aujourd'hui couplée à `Profile.progress`, avec tests communs ; conserver l'ancien suivi |
| `app/core/rule_engine.py`, `app/core/monotype.py` | Réutiliser dépendances, conflits, seed et conventions ; contrôles purs testables sans Qt ni jeu |
| `app/ui/game_mode_page.py`, `app/ui/run_dialogs.py` | Afficher règle configurée, observation disponible, alerte et limite ; corrections manuelles historisées |

Le parcours Mes parties désactive actuellement l'écriture dans le profil bridge
source. Il faut adapter la logique au Run, sans réactiver un second écrivain sur
ce profil. Les événements d'une session A ne doivent jamais modifier B après
un changement d'UUID. Dédupliquer par session/séquence et identité de l'événement,
et persister ensemble progression, résolution de rencontre et historique.

La première livraison peut calculer en mémoire les capacités et alertes de
niveau depuis le snapshot existant. Pour conserver ensuite les tentatives,
alertes acquittées et changements de plafond, une évolution explicite du schéma
Run sera nécessaire : `Run.from_dict` rejette aujourd'hui les champs et types
d'événements inconnus. Proposition : lecteur v1 conservé, conversion v1 vers v2
testée sur copie avec backup, publication atomique sous le verrou existant,
retour à la version précédente via la copie v1. Une ancienne application doit
refuser proprement v2 ; ne pas maquiller ces données en v1 ni cacher une nouvelle
structure dans les notes. Cette migration n'est pas implémentée ici.

Garder Challenge `0.1.0` et les profils historiques tant que leur contenu ne
change pas. Ne jamais modifier rétroactivement `rules_snapshot` : un plafond
effectif ajusté par le joueur doit être une décision datée propre à la partie,
avec sa provenance manuelle, sans changer le modèle d'origine. Le protocole v2
rejette lui aussi des champs inconnus : un éventuel champ de forme/objet exige
un contrat versionné et des tests de compatibilité des anciens messages.
Le statut shiny peut en revanche être dérivé côté Python depuis PID/ID32,
suivant [PK5](https://github.com/kwsch/PKHeX/blob/09e7f18fbb33635e35cf9ffcbfd3322403780f8e/PKHeX.Core/PKM/PK5.cs)
et [PKM](https://github.com/kwsch/PKHeX/blob/09e7f18fbb33635e35cf9ffcbfd3322403780f8e/PKHeX.Core/PKM/PKM.cs),
après tests et validation ; aucune implémentation n'est ajoutée ici.

## Lectures et conventions à établir

Pour Nuzlocke, conserver les inconnues tant qu'il manque une preuve de début de
combat sauvage, de résultat et de capture. Ni un Pokémon ajouté à l'équipe,
ni un changement de carte, ni la fin du flux Lua ne prouve une capture. Les
captures envoyées au PC, doubles combats, cadeaux, œufs, statiques, fuite,
surf et pêche demandent des scénarios distincts. Les tables et limites déjà
connues figurent dans [tracking-sources.md](tracking-sources.md). Aucun nouvel
offset n'est proposé dans ce document.

Le premier Level Cap utilisera le plafond numérique configuré et des niveaux
d'équipe réellement reçus. Égal au plafond est autorisé, supérieur produit un
avertissement, valeur absente reste inconnue. Les plafonds automatiques par
badge/chef ne seront annoncés qu'après source et validation de la progression.
Les PV d'équipe principale peuvent ne se synchroniser qu'après combat : ils ne
garantissent pas la détection d'un K.O. suivi d'un soin entre deux échantillons.

Monotype garde les conventions déjà codées : Souple = au moins un type choisi,
Strict = type principal choisi, Pur = uniquement le type choisi. Les 17 types
de `types_gen5.json` ne forment pas une table de types par espèce. PKHeX fournit
des tables distinctes BW et B2W2 dans
[PersonalTable](https://github.com/kwsch/PKHeX/blob/09e7f18fbb33635e35cf9ffcbfd3322403780f8e/PKHeX.Core/PersonalInfo/PersonalTable.cs)
et expose les deux types dans
[PersonalInfo5BW](https://github.com/kwsch/PKHeX/blob/09e7f18fbb33635e35cf9ffcbfd3322403780f8e/PKHeX.Core/PersonalInfo/Info/PersonalInfo5BW.cs).
Proposition : générateur reproductible avec commit source, empreinte et
provenance, clés version/espèce/forme, puis tests sur formes et évolutions.
Une forme non lue ou des types modifiés par Randomizer rendent le verdict
indisponible ; ne pas leur appliquer arbitrairement les types de base.

## Étude Randomizer — aucune exécution réalisée

Sources primaires consultées le 13 octobre 2026 :

| Solution | Constat documentaire | Travail restant |
| --- | --- | --- |
| [UPR original](https://github.com/Dabomstew/universal-pokemon-randomizer) | Dépôt archivé ; son README renvoie vers FVX | Référence historique, pas de validation PCE |
| [UPR ZX v4.6.1](https://github.com/Ajarmar/universal-pokemon-randomizer-zx/releases/tag/v4.6.1) | Version épinglable, code Gen V inspecté | Essai autorisé, reproductibilité, provenance des fichiers et compatibilité lecteur |
| [UPR FVX](https://github.com/upr-fvx/universal-pokemon-randomizer-fvx) | Continuation de ZX, support Gen I–VII annoncé dans son README | Épingler une version et auditer spécifiquement les variantes FR et son interface d'automatisation |

Dans ZX, commit `7f00eb866ed35c8fe3963f078b6a2e0979dc2b8c`,
[gen5_offsets.ini](https://github.com/Ajarmar/universal-pokemon-randomizer-zx/blob/7f00eb866ed35c8fe3963f078b6a2e0979dc2b8c/src/com/dabomstew/pkrandom/config/gen5_offsets.ini)
décrit séparément IRBF, IRAF, IREF et IRDF, version 0. Ce sont des paramètres du
Randomizer, **pas des adresses RAM à copier dans PCE**.
[Gen5RomHandler](https://github.com/Ajarmar/universal-pokemon-randomizer-zx/blob/7f00eb866ed35c8fe3963f078b6a2e0979dc2b8c/src/com/dabomstew/pkrandom/romhandlers/Gen5RomHandler.java)
contient notamment les opérations starters, rencontres, dresseurs et movesets.
Ces sources justifient un candidat d'étude ; elles ne valident aucune ROM dérivée.

La [CLI ZX](https://github.com/Ajarmar/universal-pokemon-randomizer-zx/blob/7f00eb866ed35c8fe3963f078b6a2e0979dc2b8c/src/com/dabomstew/pkrandom/cli/CliRandomizer.java)
accepte un fichier de réglages, une entrée et une sortie distincte. Sa liste
d'options ne comprend pas de seed ; l'appel utilisé choisit une seed dans
[Randomizer](https://github.com/Ajarmar/universal-pokemon-randomizer-zx/blob/7f00eb866ed35c8fe3963f078b6a2e0979dc2b8c/src/com/dabomstew/pkrandom/Randomizer.java),
qui possède aussi une surcharge avec seed explicite. Il faudra donc étudier
l'interface de reproduction adaptée ; ne pas inventer un argument `--seed`,
ni assimiler la seed du challenge à celle du binaire transformé.

Protocole d'essai proposé, seulement après autorisation de créer une ROM dérivée :

1. Épingler l'outil, vérifier sa provenance, sa licence, ses dépendances et ses
   empreintes ; ne pas installer Java globalement pour contourner un prérequis.
2. Utiliser une copie de travail distincte des sources et de toute aventure
   existante ; exiger une destination nouvelle, sans sauvegarde utilisateur liée.
3. Conserver versions, réglages, seed réellement utilisée et hashes entrée/sortie
   dans un manifeste local. Vérifier l'entrée inchangée et deux reproductions.
4. Tester démarrage, premier Pokémon, rencontre, combat, sauvegarde et reprise
   dans DeSmuME sur cette dérivée ; vérifier séparément les lectures Lua.
5. N'activer que les combinaisons validées. Des types/évolutions modifiés invalident
   les tables standard Monotype/familles ; le code de jeu seul ne prouve pas
   la compatibilité. Le manifeste d'isolation actuel interdit justement un
   remplacement silencieux de la ROM : créer une nouvelle aventure dédiée.

Aucun outil Randomizer, binaire Java, ROM ou sauvegarde n'est distribué par ce
changement documentaire. Aucune ROM dérivée n'a été créée.

d'écriture RAM nécessiteront une décision explicite et une étude distincte de
